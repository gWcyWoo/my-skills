# arv · 四维代码审核

由主会话确定范围、分派审查、复核证据并裁定。整个审核保持只读，不接触设备，不修改被审查的文件或 Git 状态。

```text
$arv [--self] [--help]
  默认      制定计划 → 并行分派四个只读审查 → 主会话复核并裁定
  --self   少量改动或复核本会话明确提出的修正，直接审核
  --help   显示本用法并结束
审核范围、确认的需求、执行者声称已完成的事项、证据路径和回复渠道来自当前对话。
```

## 确定范围

1. 遇到 `--help`，只输出上面的用法。用户指定 `--self` 时，只有改动仅几行或复核本会话明确提出的修正才适用，直接做有针对性的读取和证据核对。即使直接审核，也要覆盖四个维度中适用的检查点。
2. 确认仓库和 worktree、比较范围、排除项、用户确认的需求、执行者声明、证据路径和回复渠道。仅在缺失信息会实质影响审核结论时询问。需求原文应来自当前请求、请求指定的文件或本会话先前确认的内容；没有用户确认的需求原文时，需求范围审查无法进行，列入“未能核实”，结论为不通过。先收集一次共同事实，包括 `git --no-optional-locks status --porcelain`、对应的提交记录和 diff 统计、证据文件清单。提交范围尽量固定到提交 SHA。审核未提交改动时，明确是否包含暂存、未暂存和未跟踪文件，并为四个审查员提供同一范围。若审查中发现范围内的工作树内容变化，重查受影响的证据。
3. 简述审核边界、涉及文件和每个维度要回答的问题。交接仓库约定、历史发现及已裁定事项。正式分派前只读这些共同事实，详细执行路径留给审查员。

## 四项并行审查

读取 [只读审查员说明](references/reviewer.md)，把说明及填好的任务简报分别交给四名独立审查员，每人只负责一项。未提供的简报项写明缺失。

- `boundary`（需求范围）将每个改动块以及每个新增、删除、重命名文件对应到用户确认的具体需求点。任何不属于需求点的改动都算越界，无论大小；需求实现或验证不可缺少的接线与测试属于范围内。属于需求点但超过所需的闲置辅助代码、死代码等交给 `overdesign`。需求措辞无法判断归属的改动列为需求问题，不定级。
- `correctness`（功能正确性）核对实际行为与需求、边界值和失败路径。检查测试是否经真实入口到达断言，以及每项关键测试能抓住哪种具体错误实现。区分行为断言确实失败的证据和仅编译失败的证据。
- `overdesign`（过度设计）核对需求范围内的改动是否最小，是否有顺手重构、闲置代码或推测性参数与抽象。提取共享组件时，确认至少两个真实调用点确实需要它，并核对仓库约定；超出需求范围的线索交给 `boundary`。
- `impact`（对其他功能的影响）查找共享符号的调用方，按需跨模块检查其他流程、测试与隔离测试包、构建验证脚本、资源和本地化。确认改动没有影响需求边界外的行为。项目已有的验证约定以简报为准，例如该项目已确认使用 MockWebServer 时，不要求真实后端冒烟测试。

在审查仓库并行启动四个子会话，分别命名为 `boundary`、`correctness`、`overdesign`、`impact`。各自从标准输入接收说明和对应简报，使用不同的临时输出文件，临时目录放在被审查仓库之外。使用当前 Codex 配置的默认模型。

```sh
codex -a never exec --json --sandbox read-only --disable hooks --ephemeral \
  -C "$review_repo" --output-last-message "$report_file" - \
  < "$brief_file" > "$event_file" 2> "$error_file"
```

收集每个进程的退出状态及最终报告。只读取最终报告和定位错误所需的事件，不向主会话转发完整 JSONL。子会话失败时按实际错误尝试恢复。仍无法取得某个维度的报告时，主会话补做可完成的核查，并注明分派失败和剩余验证缺口。

## 复核与裁定

- 亲自打开每条发现引用的 `file:line` 或日志，沿必要的调用路径确认触发条件和影响。降级、移除或标为未能核实的依据来自本轮读取的证据。
- 每个维度至少抽核一条决定结论的通过证据。安全、隐私或数据变更按风险多查。发现某条决定性证据有误时，重新检查该维度的其他关键结论。
- 证据冲突时直接查源码或日志裁定。对每条 `CROSS_ASPECT` 说明已覆盖、经补查后的结论或超出范围。
- 按以下顺序裁定：先核对需求和排除项，再判断功能正确性与其他流程的影响，最后判断是否存在可避免的复杂度。超出用户确认需求的改动严禁通过，至少记为 P1，最小修正为撤销对应改动块；只要仍有越界改动，结论就是不通过。需求措辞无法判断某个改动归属时，列入“未能核实”，不定级，在需求澄清前结论为不通过。
- 非最小改动、行为副作用和死代码残留都属于发现；功能正确也不能抵消过度设计。无法抓住预期缺陷的测试属于发现。执行者声明已验证但缺少归档日志时，记为 P2 证据缺口，运行结果列入未能核实。已裁定事项不重复提出。
- P0 用于发布阻断、数据丢失或严重安全问题，P1 用于合并前必须修正的问题，P2 用于建议修正的非阻断问题。根据实证决定通过、不通过或有条件通过。影响通过条件的缺口写清楚。

## 交付

```text
【审核结论·<执行者或任务>（<范围>）】通过 | 不通过 | 有条件通过

== P0/P1/P2 ==
<n>. [级别] <file:line> — <问题> — <触发条件及实际后果> — <最小修正> — <验证方式>

== 已核实通过的审核点 ==
<按适用维度给出已复核的证据位置，并说明 CROSS_ASPECT 的处置>

== 未能核实 ==
<事项和原因>

本会话未接触设备。
```

在当前对话展示完整结论。仅在用户明确授权通过其他渠道发送时，使用可用且对应的工具发送同一文本。渠道不可用时，说明实际交付位置。交付后结束。

# 面向 ICP 的交互描述

中文自然语言，主编号从1连续递增。一个编号对应一个触发事件；复杂分支可用 2.1、2.2。固定标签辅助理解，不要求每个简单行为填满所有标签。每条必须可从 trigger 追到 behavior/result；状态、数据来源和后续条件不得省成「正常处理」。

```text
页面约定：
入口参数：名称、来源、是否必需及缺失时的已实现行为。
初始状态：控件初值、默认选中项、可用性及存储回填来源。

1.交互名称【行为/数据】
作用对象：区域 + 控件文案/语义名称。
触发：具体操作或生命周期事件。
前提：可判定条件及不满足时的行为。
执行：实际操作顺序；接口使用 API:METHOD /path。
数据：参数赋值来源、返回字段到页面/状态/存储的映射。
状态：执行前、执行中、执行后的可观察变化。
后续：按条件进入第N条，或明确结束。
```

上面是结构模板，不是要求给代码添加这些行为。未涉及的标签可省略；未找到必要信息则记录缺口，不填虚构值。

## 标记

统一输出大小写：`API:`、`global:`、`redirect:`、`toggle:`。读取旧文档时容忍 api/API 差异，但输出规范化。

- `API:POST /path`：方法及路径来自实际调用链，注明用途、参数来源、响应字段、业务成功判据；共用同一路径不同方法分别记录。接口标记本身不入页面队列。
- `redirect:完整标题`：描述触发控件、条件、传参、push/replace/清栈等实际导航语义、返回后是否刷新。不是所有跳转都来自点击，自动跳转仍写真实触发。
- `toggle:完整标题`：弹窗/Drawer 等，描述打开方式、参数、关闭方式、确认/取消、返回值及宿主如何使用。
- `global:完整标题`：表格中存在的通用组件/能力。记录使用位置、变体参数和宿主事件，公共行为在目标行单独提取。没有对应行时列出未映射能力，不创建虚假标题；宿主现有行为仍可草拟。

每条跨页引用先核实标题存在。代码符号不是表格标题。不同来源同名时，内部引用使用完整来源定位；正文需要同时注明来源链接，不能静默交给 ICP 一个含糊的同名目标。

## 必须回源核对的细节

- 初始化次数、返回刷新、语言切换、登录态、缓存与本地持久化。
- 输入长度/字符/格式化/光标规则、默认值、显隐、disabled 条件。
- 当前列表项身份、路径/query/body 参数、格式转换、枚举分支、响应回填。
- 串行/并行、去重、防抖、节流、过期响应、轮询间隔及停止条件（仅写源码实际存在者）。
- 请求中、业务失败、网络异常、空数据、重试及保留/清空状态。
- 权限、系统选择器、WebView/深链回调、取消、返回、离开时资源清理。

读取共享网络层和路由守卫，不能把它们的统一错误/鉴权处理误写成页面没有处理。被服务端决定而代码不能确认的行为明确标为待核实。

## 埋点提取与核对

埋点属于交互的一部分，包括业务行为统计及实际接入的设备/风控采集。以当前源码调用链为基准，不能用旧表、埋点命名或 SDK 事件定义代替实际接入证据。

### 发现与追踪

从页面、状态管理、路由宿主和公共组件查实际调用、包装器及生命周期监听；用 `rg` 查找项目真实使用的采集符号，再沿 import、注入和回调读取事件处理器、统计状态、会话、队列及网络出口。查 SDK 调用方反向补漏，不能仅靠固定关键词判断覆盖。

每个采集点追清三层事实：

1. **触发**：动作/生命周期、控件或当前项、分支前提、事件标识、参数来源，以及与业务操作的先后关系。取消、返回、失败、重复点击分别按实际接线判断。
2. **统计**：事件到最终字段的映射、枚举、默认/缺失值、计数增量与重置、计时起止/暂停/累计及单位。若只更新本地状态，不得描述为立即上报；直接发送的采集不虚构统计层。
3. **发送**：发送或会话结束/取消条件、跨页复用、新老客等分支、批次/汇总、接口或 SDK 出口、最终载荷及鉴权归属、成功判据、持久化/去重/重试/异常隔离。仅写源码实际实现者；外部 SDK 内部不可见时注明边界和未确认项。

区分事件标识、设备采集阶段、授权策略阶段和行为上报阶段；即使都名为 `stage` 或取值相同，也须各自追踪用途。检查采集失败是否影响业务流程，不能按惯例假设互不阻塞。

### 写入对应交互

在触发行为所属编号下增加“埋点：”说明；独立生命周期或汇总发送可有自己的编号。内容至少覆盖适用的触发条件、事件/参数、统计字段与规则、发送时机及异常行为。禁止以“参与原有行为采集”“按现有接线记录”等表述替代这些事实。

公共统计与发送规则可在已核实的组件行或流程所属行定义一次，其余行明确引用准确标题和编号，并写出自身参数及差异。无独立表格标题时写在宿主行，不能虚构 global 目标；正文不能只引用本地台账，ICP 必须能从交互描述及 api_description 得到还原所需规则。上报接口仍使用 `API:` 并纳入 api_description。保留必要的事件标识、载荷字段及业务常量，不要求新实现沿用旧类名。

### 埋点台账与通过条件

逐页本地产物增加 `tracking_audit`：

- `version: 1`、`status: complete / gaps / none_found`；none_found 仅表示已查范围内未发现实际接入，不代表整个应用没有埋点。
- `checked_scope`：检查过的入口、宿主、组件、采集包装器和共享依赖；保存证据及文件指纹。
- `points`：每项含唯一 id、标题/变体、触发与条件、调用点 evidence、事件及参数、统计字段/规则、发送规则、对应描述位置（来源、标题、交互编号）、status（covered / gap）和具体缺口。证据沿用现有文件/符号/行号/指纹格式。
- `excluded`：发现但未实际接入、不可达或超出范围的候选及理由/证据；不能把不确定项归为已排除。

同一事件在不同触发点或不同参数/条件下分开记录；公共实现可以共用证据，但保留各宿主调用映射。跨页会话记录创建、传递、结束/取消及汇总归属，不能只在创建页写一句“开始采集”。

写前做双向核对：从 points 查每个实际采集点是否准确写入；从正文每条埋点说明回查实际调用及下游实现。使用确定性工具检查 id 去重、标题/编号引用、证据指纹和未覆盖集合；模型核对条件、计算与时序语义。关键词命中、点数相等或脚本通过都不能单独证明完整。

仅当已查范围明确、所有实际采集点均 covered、每条描述都有依据且不存在影响还原的缺口，才标 complete；未接入的 SDK 能力不得凑入覆盖数。没有实际采集点时保留 checked_scope 与 none_found，正文无需虚构埋点。全局补漏发现遗漏后，重新核对受影响页面。这里验证代码与文档一致，不运行应用或调用业务接口来冒充运行时上报验证。

## 源码依据及 ICP 输入

逐页本地产物含：`interaction_description`、`api_description`、`evidence`、`references`、`gaps`、`old_description_diff`、`tracking_audit`。

evidence 按交互编号保存绝对文件路径、符号、经工具读取的行号和文件指纹；正文不放旧代码类名/绝对路径作为新实现约束。references 为语义理解后的有向边，包含 kind、source_interaction、target 来源和标题、condition、params、代码依据。

api_description 按接口列出客户端观察：用途、METHOD/path、鉴权行为、请求位置与字段来源、响应字段用途、错误处理。区分后端原始响应与网络层解包后的对象。未核实的 schema 或类型不编造。

ICP 的 Stage 2 自行把自然语言映射到目标 component_name 和原子交互图；CTI 不预造 component-binding.json。转换器的编号是追溯编号，不是已绑定的 ix_id。API 清单需单独传入 ICP 的 api_description；只在交互正文出现 API 标记不能保证 ICP 获得接口输入。正式契约验证和缺失契约策略由后续 ICP 流程处理，CTI 不隐式授权 mock。
